# Plan: 6M TPS on window 1 (2026-11)

Status: opened 2026-11-14 on the user's decision. Predecessor: `docs/PLAN_HOLD_5M_2026_11.md`
(`main` reads 5.06-5.12M on four legs after four fixes).

## 1. Target

The all-Rust fleet7 X22 round on `main` reads 6M transactions a second on window 1, every block valid,
gov5 byte-compatibility kept. At 200,000 transactions a block that is a 33.3 ms mean block gap; today's
is about 39 ms.

## 2. Where the 39 ms goes (main legs H5C0 / H5D0, window-1 means)

| phase | ms | note |
|---|---|---|
| sealed_at | 37.1-37.8 | bound by the root job |
| par_exec (wall) | 28.6 | 32 threads, 757 ms of CPU; state reads ~500 ms of it |
| root_compute | 29 | apply 24, leaves 8-9, writes 6.9, retire 3.4 |
| root ops (before the gate) | 13-14 | encode 9, sort 5.7 |
| root_gate_wait | 4.3-4.6 | 0.9 on the tagged build |

Every single lever after X17 moved the round by 1.5% or less, and a bigger block was closed in October
(cycle proportional to size, stage ck). 6M needs about 5 ms off the root job and about 5 ms off the
execution: the seal is bound by both.

## 3. Stage 0: measure before choosing (this plan's first step)

| id | question | how | done when |
|---|---|---|---|
| M1 | which floor binds at a 33 ms gap | two ceiling legs with bench-only knobs: one skips the root computation, one skips the execution; never a product path | gap of each ceiling leg, twice |
| M2 | can the supply reach 6M | ingest rate, recover and queue headroom from the existing legs; a supply-only measurement if they cannot say; a replay set large enough for three windows at 6M | a number for the supply ceiling |
| M3 | best transactions a block | sweep around today's 200,000 (150k-250k), each size at least twice, interleaved, on `main` natives | TPS and gap per size, with spread |

## 4. Candidate work after stage 0 (estimates, unmeasured)

- Read prefetch on the execution path: sender and recipient are known before execution; the same
  software pipeline that took the seeded held-slot pass from 61 to 24 ms under shared cores.
- Root job structure: ops encoding inside the execution batches; apply and writes per shard in parallel.
- root_gate_wait: follows the parent's root job; should shrink with it.

  Reading (single legs are +-2%, differences under ~10% between single legs are not conclusions):
  - Taking the Merkle hashing out saves about 3-4 ms of the root job and moves TPS by ~1-2%: the
    hashing is not what binds. Taking the execution reads out cuts par_exec 29 -> 12-13 ms and, alone,
    moves TPS by -2..+4% (root queue still binds). Removing both reads 5.39-5.48M (+6%), cycle 36-37 ms.
  - With the hashing and the reads gone the root job still takes 32 ms: the ops encode (13.5 ms,
    before the gate), the apply (entry appends, index inserts, retired slots, undo record) and the
    parallel leaf bookkeeping. The cycle (36-37) is that root job plus the gate wait (4 ms): the serial
    root queue is the floor, and it is made of structure work, not of hashing or of state reads.
  - 6M needs a 33.3 ms cycle. The cheapest lever per the table is the root job's non-hash part
    (encode, sort, apply, entry and index writes), by ~4-5 ms on top of the exec reads; neither alone is enough.
  - Supply: the skip-both legs sent 5.1-5.2M/s with the pool at its 2.5M cap and the flood workers
    waiting on the node; supply is not the limit up to 5.5M. A supply-only leg (no node work) is still
    unmeasured and would give the exact ceiling.
  - The first skip-exec attempt collapsed (160k TPS, 33k a block): the stand-in balance 2^100 was below a
    60-transfer run's gas-limit x fee-cap budget (1.26e30 at the 1e24 cap); fixed with 2^200 (0a99ae7eb,
    test `the_ceiling_stand_ins_cover_a_fleet_run_at_the_fee_cap`). Collapsed legs kept as `...OLDMEMF`.

- **2026-11-19, execution read prefetch (`perf/exec-read-prefetch`, f3d1be7a2, not merged).** A bulk
  account read per batch (`N42_EXEC_READ_BATCH=1`: senders, recipients and the beneficiary resolved up
  front through every layer, the QMDB index looked up as a pipeline with the entry record prefetched).
  Pair ERB against the root-job natives, three legs (the second control leg yielded the box to another lane's request at the leg boundary):

  | leg | TPS | par_exec | reads + resolve (thread sum) | transact (thread sum) | sealed_at |

  | ERBa (prefetch) | 5.03M | 28.1 | 22.5 + 461.2 ms | 162.8 ms | 37.6 |

  - The read time moves into the resolve step almost whole (518 -> ~480 ms of thread time, -7%):
    the batch is bound by memory latency on reads that 32 threads already issue concurrently, and
    software prefetch inside one thread adds little. par_exec -1 to -1.7 ms against one control,
    sealed_at and TPS inside leg noise. Not a lever; the knob stays a candidate, default off, and the
    branch is kept unmerged.
  - The microbench (`exec_read_profile`, 2M keys) predicted this size (-0.7 ms of 11.5).
  - tc=7 on every leg here and in RJA/RJP is the seven view-1 start-up timeout lines (one per

    defect. Foreign load during the legs

  - Execution's floor is the number of DRAM reads per transfer, not how they are issued; the next
    step there is a state layout that needs fewer of them, which is design work, not a knob.
