# Plan: 6M TPS on window 1 (2026-11)

Status: opened 2026-11-14 on the user's decision. Predecessor: `docs/PLAN_HOLD_5M_2026_11.md`
(`main` reads 5.06-5.12M on four legs after four fixes).

## 1. Target

The all-Rust fleet7 X22 round on `main` reads 6M transactions a second on window 1, every block valid,
gov5 byte-compatibility kept. At 200,000 transactions a block that is a 33.3 ms mean block gap; today's
is about 39 ms.

## 2. Where the 39 ms goes (main legs H5C0 / H5D0, window-1 means)

| phase | ms | note |
|---|---|---|
| sealed_at | 37.1-37.8 | bound by the root job |
| par_exec (wall) | 28.6 | 32 threads, 757 ms of CPU; state reads ~500 ms of it |
| root_compute | 29 | apply 24, leaves 8-9, writes 6.9, retire 3.4 |
| root ops (before the gate) | 13-14 | encode 9, sort 5.7 |
| root_gate_wait | 4.3-4.6 | 0.9 on the tagged build |

Every single lever after X17 moved the round by 1.5% or less, and a bigger block was closed in October
(cycle proportional to size, stage ck). 6M needs about 5 ms off the root job and about 5 ms off the
execution: the seal is bound by both.

## 3. Stage 0: measure before choosing (this plan's first step)

| id | question | how | done when |
|---|---|---|---|
| M1 | which floor binds at a 33 ms gap | two ceiling legs with bench-only knobs: one skips the root computation, one skips the execution; never a product path | gap of each ceiling leg, twice |
| M2 | can the supply reach 6M | ingest rate, recover and queue headroom from the existing legs; a supply-only measurement if they cannot say; a replay set large enough for three windows at 6M | a number for the supply ceiling |
| M3 | best transactions a block | sweep around today's 200,000 (150k-250k), each size at least twice, interleaved, on `main` natives | TPS and gap per size, with spread |

## 4. Candidate work after stage 0 (estimates, unmeasured)

- Read prefetch on the execution path: sender and recipient are known before execution; the same
  software pipeline that took the seeded held-slot pass from 61 to 24 ms under shared cores.
- Root job structure: ops encoding inside the execution batches; apply and writes per shard in parallel.
- root_gate_wait: follows the parent's root job; should shrink with it.
