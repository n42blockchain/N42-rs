# 7 节点 E=7 线计划(2026-10-28 起)

分支 `e7/independent-execution` 维护;审计线在 `audit/5m-full-2026-10`(`docs/PLAN_5M_AUDIT.md`),两条线分开。
目标:把"每个节点独立执行(E=7)、真实区块形态、多主机网络"三个数字建立起来并逐步提高。

## 0. 前提与约束

- 任何改动都按 bench 对规则验证(`scripts/fleet7-runs`,单轮差异 <10% 不可见),不拿掉 X22 已采纳的优化,除非 E=7 的 bench 对证明它在 E=7 下有害,并记录在 `docs/NATIVE_FLEET7.md`。
- 审计线的修复合入 main 后再并入本分支;本分支不自行修改审计范围内的安全相关代码。
- Linux bench 主机目前断电,本线的所有测量都排在主机恢复之后。

## 2. 阶段

1. **E=7 单机基线。** 主机恢复后以 X22 配置(去掉 `N42_IMPORT_ONCE`,`F7_EL_MAP=0..6`)
   跑三对,确定 E=7 的当前数字和瓶颈分解(`fleet7-phases.py`),并列出 E=1 专用、
   在 E=7 下不成立的优化。
2. **真实区块形态。** 定义两到三种形态并固化为回放集:纯转账多账户(每块约 15 万
   账户)、ERC-20 转账、混合合约调用;每种形态记录 TPS、占用率和周期分解。
   在此之前,按 `docs/BLOCK_SHAPE_SURVEY.md` 的线性模型(0.40 s + 2.8 us/账户)给出预期。
3. **签名真实验证。** 关闭单网关背书,跑逐笔验签(或真正的 f+1 多网关),量出供给侧的代价。
4. **多主机网络。** 至少三台主机:节点分布、真实网络时延与带宽、(可选)注入延迟/丢包;
   需要准备主机、`fleet7-env.sh` 的多主机版本、跨主机的启动与采集脚本。
5. **逐项提升。** 每一项改动都按 bench 对规则验证,在 `docs/NATIVE_FLEET7.md` 记录。

## 3. 已识别的差距(2026-10-28 盘点)

1. **帧的分发是单机假设。** bench 中每个节点之所以持有一个区块引用的全部帧,是因为压测器
   把每笔交易直接发给每个执行层的本地 ingest(`scripts/fleet7-bench.sh` 407-415 行,
   `F7_INGEST_ALL`),而不是节点之间传播帧。成熟度审计后,attested frames、`N42_TX_INGEST_DIRECT`
   和 `N42_INGEST_VERIFY=shard|leader` 下 ingest **拒绝非环回绑定**(`N42_TX_INGEST_ALLOW_REMOTE`
   也不放行)。所以多主机时帧如何到达各节点需要设计:节点间的帧传播(GossipSub 主题或
   按 id 拉取),或者每台主机一个本地网关/压测器。这是一个需要设计文档和 bench 对的条目,
   不是脚本改动。
2. **脚本全部写死 127.0.0.1。** `scripts/fleet7-env.sh` 的 authrpc、http、metrics、ingest、
   验证者 `--listen`/`--peer`(约 466-724 行)都是环回地址;需要一个主机清单
   (`F7_HOSTS`)和按主机分配节点、端口、CPU 的版本,以及跨主机的启动、日志收集和
   `fleet7-measure.py` 的输入汇总。
3. **E=7 单机的 CPU 预算不同。** E=1 给一个执行层 208 个 CPU;E=7 每个节点约 32 个
   (`fleet7-env.sh` 504 行附近的 `taskset` 说明),X22 里一些按 E=1 调出来的值
   (`RAYON_NUM_THREADS`、build pool、`N42_BUILDER_PULLER` 等)要在 E=7 下重新确定。
4. **E=1 专用的机制。** `N42_IMPORT_ONCE`(一层多密钥共享导入)在 E=7 下不存在;
   需要逐项确认其余 `adopted` 优化在 E=7 下仍然成立。

## 4. 需要准备的资源

- bench 主机修好电源(或更换 PSU)并恢复 SSH 访问;
- 多主机网络阶段所需的另外两台以上同级主机及其互联;
- 磁盘:E=7 下七个执行层各自写静态文件,单机磁盘余量需按 E=1 的约 1.4 GB/s 乘以层数重新评估。
