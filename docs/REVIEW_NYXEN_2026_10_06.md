## Hot-path findings

Crates on the hot path in `Cargo.lock`: tokio 1.53.1 to 1.53.2, mio 1.2.3 to 1.2.4, cc 1.5.1 to 1.6.0 (build). Unchanged: rayon, tikv-jemalloc(-sys/-ctl), rocksdb, blake3, ed25519-dalek, curve25519-dalek, alloy-primitives, revm 43, parking_lot 0.12. libp2p-* all change.

1. **Yamux window tuning removed (3f9ddabe8). Risk: medium, unmeasured.** `yamux_receive_window()` (default 16 MiB, `N42_YAMUX_WINDOW_MB`) and the 16 MiB buffer cap are gone; yamux 0.14 auto-tunes and the env var now only logs a warning. The old comments record why: a 12.2 MB body took 302 ms on the default window, and a small buffer cap closed the connection (`buffer of stream grows beyond limit`, 18-36 per node per round) while the loop awaited an import. Affects the gossip body path (105 MB at 300k tx) and every per-view vote/proposal message sharing a connection. The loop343 legs use `F7_DIRECT_PUSH=1`, which sends the body over the direct TCP channel, so the effect on the headline number should be small, but the fallback and late-joiner paths ride yamux. The only new test crosses 2 MiB; nothing exercises 12-105 MB.
2. **Compact body cap (1617435f3), per block, negligible cost, rejects above 1,048,576 txs.** The loop343 runs use `F7_GASCEIL_ARG=4200000000` at 21,000 gas, so about 200k tx per block: 5.2x headroom. A leg that raises the gas ceiling past about 22e9 would have its bodies refused. `MAX_BLOCK_TXNS_INDICES` is now the same constant.
3. **Raw channel caps (1617435f3), per frame, nanoseconds.** Bodies and requests: 256 MiB (a 300k-tx body of 105 MB fits 2.5x); hash lists: (256 MiB)/32 = 8.39M hashes (a 200k-hash, 6.4 MB list fits 42x); 36-byte entries: 7.46M; request lists: 256. Execution data now also rejects trailing bytes, unknown payload kinds, flags other than 0/1, and counts larger than remaining bytes / element minimum (4, 32 or 44): all checked once per list, not per tx; legitimate encodings pass (the encoder writes u32-prefixed items). The compact fill check `n <= remaining/8` and `count <= rest/4` in `decode_txns` hold for 200k-tx bodies (about 15 KB descriptions are far above the 8-byte minimum).
4. **Ingest frame bytes (8779bbdd6), per tx, about 1 ns.** One add and compare per tx: 3M tx/s is about 3 ms of CPU per second. 64 MiB per frame against 500 tx x 81 KB = 0.04 MB (and the 10,000-tx frame cap times 162 B = 1.6 MB). The replay set's frames stay under 10,000 tx, so nothing legitimate trips it. Attestation count check is in `mobile-verify` only (mobile service), not on the frame-attestation path (`N42_FRAME_ATTEST_MIN`), so attested frames are unaffected.
5. **Ed25519 batch verifier (8779bbdd6), per batch.** The linear key-dedupe scan becomes a `HashMap<[u8;32]>` (SipHash, 256 entries per batch at `N42_ED25519_BATCH=256`). All-distinct senders: faster (about 30 us down to about 8 us per batch). Few repeated senders (flood-style): slower by about 20 ns per tx, which is about 60 ms of CPU per second at 3M tx/s (0.06 core, spread over the recover pool). Point order and results are preserved (tests added).
6. **QMDB writer (7aaeb7f86 and bincode swap), per block, likely under 1-3 ms.** `delta_since` for a file-backed forest now retains dirty slots up to `next_slot` and adds a `slot_active` lookup plus a `(slot,false)` entry for each appended-then-retired slot, so deltas grow with the blocks they span (up to about 9 bytes x 150k per extra block). `bincode::serialize(delta)` (node_state.rs, `N42_PERSIST_QMDB_IN_SCOPE=1` puts it in the block scope) now goes through bincode_reloaded's serde adapter; on about 2-3M elements per second that is a few ms per second in total, but 1-2 ms per block is the same order as the 6 ms the freeze work just won. Bytes are claimed identical to bincode 1.3.3 (three real files re-encoded byte for byte, tests included). The change is a correctness fix for restart (checkpoint active bits), not a root change; it cannot change roots in flight. Static-file writer: NippyJar uses the same codec only for its per-jar config, not per row.
7. **Not touched:** queue, build path, vote road (h2-consensus messages: the bincode swap changes no bytes), jemalloc and THP settings (the THP `prctl` is only `cfg`-gated), fleet env files and the loop343 runner (`scripts/fleet7-env.sh`, `fleet3-env.sh` unchanged). gossipsub 0.50 and noise 0.47 may change defaults; the GossipSub parameters are a gov5 wire contract asserted in tests, which the author reports passing, but they were run on macOS only, no Linux, no fleet.

## Verdict

Bench with these legs. Nothing rejects a frame the bench legitimately sends, and the only per-tx check costs about 3 ms of CPU per second at 3M tx/s. The two unmeasured risks are the yamux flow control (item 1) and the delta write/codec cost (item 6). Build the new tip with the same profile and flags as the `$NAT` binary of loop343 (the validation was on macOS).

Legs (each twice, since differences under 10% between single rounds are invisible; fresh datadirs, dropcache and hugeprep as usual):

1. `D` on the old binary (09a1284e4 build) against `D` on the new tip: the base line, E=1 3.0-3.2M TPS. Compare win1, total, cycle, and the fields/seal timings of `fields343.py`.
2. `F2` (freeze plus root ops, `N42_FREEZE_AFTER_SEAL=1 N42_ROOT_OPS_AHEAD=1`) on both: the best known configuration, to catch a loss on the QMDB persist step.
3. `D` with `F7_DIRECT_PUSH=0` on both (bodies by gossip over yamux): the only leg that measures finding 1; watch `buffer of stream grows beyond limit`, body arrival time and view timeouts in the node logs.
4. The fleet3 independent-execution round (1.44M) on both, for the vote road and the three-node body path.
5. One restart check on the new tip: kill a node after a `D` leg and restart it from its datadir, to confirm the new delta replay reproduces the head root (the claim of 7aaeb7f86).

If leg 3 regresses, restore a fixed receive window in `h2-net` config before taking the libp2p upgrade; if leg 2 regresses by more than 3%, profile the delta encode before anything else.
