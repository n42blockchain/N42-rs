# R3-E2: touched but unchanged accounts and the QMDB root

Status (2026-10-30): **Rust unchanged** (the current rule is pinned by a test).
A **gov5 patch is pending the user's decision** (unpushed, see
`docs/patches/gov5-unchanged-account-no-op/`).

## The finding as filed, and what was actually wrong

ROUND3 filed R3-E2 as "on a zero-fee block the parallel path does not write the
beneficiary, the serial path does (touch), so the QMDB roots differ". The premise
was wrong. **No Rust path writes the beneficiary on a zero-tip block.** Every Rust
path agrees with every other. The roots that differ are gov5's and Rust's.

A QMDB root is positional. `lib/qmdb/qmdb.go:562 Tree.Set` (gov5) and its Rust
port append a new slot even when the value is unchanged. So the question is not
"which state", it is "which writes": an account re-written with the value it already
had still moves the root.

## Evidence

member. The genesis is `n42_devnet.json` with `devBlockReward` 0, so no block reward
and no faucet. Transfers came from `examples/send_tx --tip/--value`.

- Outputs: `/data/n42-build/audit-notes/devnet/<leg>.out` and `<leg>/gov5/log/n42.log`.
- Rust binaries in every leg: main plus the send_tx flags, unmodified execution
  (`/data/n42-build/scratch-e2/bin-pre`).
- The parallel builder and parallel import never engaged on the devnet

## Mechanism

**Rust (all paths): an unchanged account is never in the bundle.**

- The serial executor touches the beneficiary on every transaction:
  - revm-handler 43.0.3 `post_execution.rs:122-124` `reward_beneficiary` calls
    `load_account_mut(beneficiary).incr_balance(tip × gas)`;
  - revm-context-interface 43.0.2 `account.rs:382` `incr_balance` touches first;
  - the N42 transfer path's `fast_transfer.rs:665` does the same.
- A zero-value transfer touches its recipient: revm-context 43.0.3
  `journal/inner.rs:474`, `fast_transfer.rs:661`.
- But revm-database 43.0.1 `bundle_state.rs:584-592`
  (`apply_transitions_and_create_reverts`) inserts an account into the bundle only
  when `transition.create_revert()` is `Some`. A transition whose info and storage
  are unchanged has no revert, so the account is left out.
- The QMDB op conversion maps the bundle to leaves one to one, so no leaf.
- The parallel paths commit the beneficiary only for a non-zero credit:
  `parallel_transfer.rs:4852` and `:5325`, `payload.rs:3376`. They agree with the
  serial path.
- Pinned by `parallel_transfer::tests::an_unchanged_account_writes_no_leaf_on_any_path`.
  It covers the serial executor, fold, graft, sender groups, the plan made ahead,
  the merge behind and the build path's shards, on a zero-tip block with zero-value
  transfers to a funded account: neither account is in any bundle, and
  `sorted_operations_from_execution` emits no op for either.

**gov5 (origin/main `ec04b375`): it depends on the path and on what was loaded
before.**

- Serial `IntraBlockState`, case one: the account is not yet loaded in the block.
  - Fee credit: `internal/state_transition.go:728` `creditFee` →
    `IntraBlockState.AddBalance` (`modules/state/intra_block_state.go:898`).
  - `AddBalance` journals a `balanceIncrease`, for any amount including zero.
  - That journal entry dirties the address (`journal.go:302`).
  - `FinalizeTx` (`:1288`) materialises the pending increases
    (`pendingIncreaseAddrs`, `:1301`) and moves the journal's dirties into
    `stateObjectsDirty`.
  - `computeRootViaComputer` (`:1604`) hands every dirty live account to
    `QMDBRootComputer.ComputeRoot` (`commitment/qmdb_root_computer.go:828`). That
    issues a `Set` for each one, re-appending the unchanged value.
- Serial `IntraBlockState`, case two: the account is already loaded.
  `stateObject.AddBalance` (`state_object.go:558`) returns on a zero amount without
  journalling, unless the account is empty. So the same account is not written if
  anything read it earlier in the block.
- Parallel commit: `parallel_commit.go:267` and `parallel_apply_ibs.go:104` skip a
  zero `CoinbaseDelta`. A `feeSink` (`state_transition.go:399`) bypasses
  `AddBalance` entirely.

## Generalisation

The rule is not about the coinbase. In gov5's serial path, any account whose first
access in a block is an `AddBalance` is written even if it ends unchanged:
- the coinbase credited a zero tip;
- the recipient of a zero-value transfer that was not loaded yet (the cb-ser leg is a
  second instance, not a confound);
- a zero withdrawal or reward.

The same account loaded first is not written. The Ethereum state root is blind to an
unchanged account by construction (an MPT update with the same value changes
nothing). revm's bundle follows from that, and so does every Rust path.

## Options

1. **Emulate gov5 in Rust.** Pass the beneficiary (and, in general, every account
   gov5 would dirty) into the bundle-to-ops conversion at about 13 root sites, and
   reproduce gov5's load-order dependence. That dependence is not reconstructible
   from a bundle (it needs the order in which gov5 would first touch each account),
   and it differs between gov5's own serial and parallel paths. Hot path, and no
   single rule to copy. Rejected.
2. **Make gov5's root a function of the state change (recommended).** Gate it on a
   chain-config time, the same pattern as the header-field decision. The patch:
   - adds `unchangedAccountNoOpTime` (nil = never);
   - from that time, `computeRootViaComputer` leaves out a live account whose nonce,
     balance and code hash equal its original and that has no storage or code write,
     no wiped storage and was not created;
   - leaves deleted and self-destructed accounts alone;
   - exempts `SystemAddress`, which the Prague system calls touch every block;
   - sets the rule in HotStuff's `Finalize` (build and verify path) and in replay-v2
     from the block's time;
   - under the rule, gov5's parallel path (which already skips a zero delta) agrees
     with its serial path.

   `go build ./...` passed; `go test` of `./modules/state/` (24.8 s, including the new
   `TestUnchangedAccountNoOp` and `TestIsUnchangedAccountNoOp`), `internal/consensus/hotstuff`,
   `params`, commitment, snapshot and witness passed. The devnet legs above passed.

Shape (b), the coinbase loaded earlier in the block, needs no separate leg under
option 2. Under the rule an account's write depends only on whether its state
changed, never on when it was first loaded, so the loaded and unloaded cases are the
same case.

## Operator step (option 2)

- **New chain:** set `"unchangedAccountNoOpTime": 0` in the genesis config.
- **Running chain:** pick a future time. Upgrade every gov5 member to the patched
  binary before it, and put the same value in every member's genesis config. n42-rs
  ignores the field because it already follows the rule.
- **Base rebuilt from old-chain data (replay-v2):** set the time in the chain config
  the base is rebuilt under, at or before the rebuilt chain's first block. replay-v2
  reads it per block (`engine_v2.go`, before `IntermediateRoot`). Then run the fleet
  on a genesis carrying the same time.
- **Until then:** a mixed fleet must not carry zero-tip transactions or zero-value
  transfers to existing untouched accounts. On today's chains the per-block
  `devBlockReward` keeps the coinbase changed, which is why this stayed latent, but
  zero-value transfers are not covered by that.
